# LLM rubric · Top 3 badcase 修复记录

> 对应 7 天行动清单 D3：分析 badcase → 修 Top 3 → 重跑对比。
> 评测口径：真实 DeepSeek 跑 Agent + model-as-judge；离线，不是线上 A/B。

---

## 1. 三个 badcase 的根因

| case | 表面问题 | 真正根因 | 为什么 pass/fail 看不出来 |
| --- | --- | --- | --- |
| rubric-018 低预算加预算 | 旧 judge 判为“编造余额/ROI”，且仍提交 +10% 预算 | ① 目标账户「花间集」是**部分授权 + 缺商品交易**，没有写前门禁；② 用户说“余额不多”与工具数据（125,470 / 17 天）冲突，Agent 迎合前提；③ 旧 judge 看不到工具结果，把真实数字误判为编造 | 流程能跑完、动作也进了待确认，只是“能不能做”没人拦 |
| rubric-013 直接执行 | 称目标计划“不在已授权账户”，却又引用该计划数据 | ① L2 只列**消耗 Top 3 账户**，被误读成“授权清单”；② 目标计划事实（预算/出价/ROI）没进上下文；③ 系统确实没有“计划级日预算”工具，Agent 用幻觉补上了 | 没有越权执行，safety 看起来没问题；错在事实和上下文 |
| rubric-015 超幅度加预算 | 声称已提交 +20%，待确认清单为空；动作落到别的账户 | ① 没有“声称提交但工具没调用”的对账；② 计划级目标被账户级动作变相满足；③ 自动提醒会催 Agent“去提交动作” | 回复写得像“已提交”，但工具路径里没有写动作 |

三个 case 的共同点：**不是模型不会写，而是系统没把“事实/权限/动作状态”变成硬约束**。

---

## 2. 改了什么

### 2.1 目标与授权事实（`server/guardrails.mjs`，新增）

- 解析 `account_id` / `plan_id` / 账户名 / 计划名，生成**权威目标事实块**：账户授权、报表延迟、日预算、余额、近 7 天消耗/ROI/订单成本、计划预算/出价/状态；
- 明确写作用范围：点名计划时**只允许该计划**，不能用账户预算变相满足；点名账户时才允许账户级动作；
- 明确系统能力：没有计划级日预算工具，计划级只有暂停/恢复/出价 ±15%；
- 明确“L2 Top 账户 ≠ 授权清单”“用户口述与工具数据冲突时以工具为准”。

目标事实块注入 L3（所有专家）和综合决策 prompt。

### 2.2 数据缺口门禁（`server/tools.mjs`）

- 账户缺商品交易（净成交/退款不可用）或授权不完整 → 四个写工具（预算/暂停/恢复/出价）**一律拒绝**，返回“只能观察/澄清或先补授权”；
- 报表延迟只作为非阻断缺口提示，不误杀正常动作；
- 决策单统一带上 `dataGaps`，确认页能看到缺什么。

### 2.3 动作状态对账（`server/orchestrator.mjs` + `guardrails.mjs`）

- 专家文本里出现“已提交/已执行”，但该专家**没有成功的写工具记录** → 确定性改写为“未提交/未执行”，并加一行系统校验说明；
- 综合结论同样对账：没有 pending/operation 就不允许写“已提交/已执行”；有 pending 却不允许写“本轮无待确认动作/0 笔”；
- 方向自洽检查：同一句“降低 X%（A→B）”但 B>A（或反过来）、或“由 A 升至 B”但 B<A → 方向词改为中性的“调整 / 变为”；
- 样本量规则：计划日均订单 < 10 单 → 标为“样本不足”，不能作为加预算依据；
- 超限/跨账户规则：点名计划时不允许用账户预算变相满足；跨账户搬预算若方向与 ROI 相反，先澄清、不直接提交两笔；用户说“直接改/不用确认”时不催动作；
- 移除了原来“催投放专家提交动作”的硬提醒；只有任务确实期望动作且未被数据缺口阻断时才提醒，且明确允许“未提交 + 原因”。

### 2.4 评测 harness 修正（`scripts/eval-llm-rubric.mjs`）

- judge 现在能看到**工具调用参数 + 返回结果 + Agent 收到的 L1/L2/L3 上下文**（v0.2）。旧 judge 只看工具名，无法核对数字，会把真实工具数据/上下文数据误判为“编造”；
- “只观察类” case 的一票否决改成显式集合：`observe / report_only / report_or_observe / observe_or_block / observe_or_clarify`；
  - 旧逻辑只要 action 字符串里含 `observe` 就一票否决，把 `decision_or_observe`、`reduce_or_observe` 也误杀了；
- 报告记录 `judgeMode`，新增 `--judge=names|evidence`、`--suffix=`，便于同口径对比与单例回归。
- **跨 version 的分数不可直接比较**：v0.1 的 11/20 是在“看不到工具结果”的 judge 下测的；v0.2 修正了事实性测量误差。行为层面的证据（pending、是否编造、是否越权）比分数更可靠。

## 4. 全量重跑

**最终结果（2026-11-06，judge v0.2）**

- 20 个 case，20/20 有效评分；**通过 20/20（100%）**；
- 维度均分：事实 4.65 / 数据缺口 4.85 / 动作 4.70 / 校准 4.05 / 解释 4.75 / 安全 5.00；
- 运行失败 0，judge 失败 0；
- 最低分 4.17：rubric-006（周报）、rubric-009（样本不足）、rubric-011（品牌），问题都是“数字来源/溯源表述”而非越权或编造；
- 报告：[llm-rubric.report.md](llm-rubric.report.md)。

**怎么读这组数**

| 口径 | 结果 | 说明 |
| --- | --- | --- |
| baseline（judge v0.1，只看工具名） | 11/20（55%） | 旧 judge 无法核对数字，factuality 被系统性低估 |
| 修复 + judge 只看工具结果（v0.2 首跑） | 14/20（70%） | 已修掉三个目标 badcase，但 judge 看不到 L1/L2/L3 上下文，仍误判“报表延迟/大盘 ROI”为编造 |
| 修复 + judge 看工具结果与上下文（v0.2 最终） | **20/20（100%）** | 同一 20 例；009/014 为补充修复后单例 `--merge` 并入 |

> **不要把这 100% 当成泛化准确率**：这 20 个 case 同时用于定位和修复，存在过拟合；judge 与 Agent 同源，有自评偏见；下一步要用未参与修复的 50–100 例复核，并人工抽检 20%–30%。

---

## 5. 仍然存在 / 下一步

- **过拟合风险**：20/20 是在参与修复的 case 上测的；下一步建 held-out 50–100 例，先测不修，再决定改什么；
- **溯源仍是薄弱项**：006/009/011 的扣分都在“这个数字来自哪个工具/哪一层上下文”说不清；下一步让工具结果带 source id，合成时强制引用；
- **case 前提与 mock 数据冲突**：rubric-018（余额 125,470 却被说“不多”）、rubric-004（拾光 ROI 更低却被说更高）。本轮 Agent 学会“指出冲突、以工具为准”，但 case 本身应改成真实低余额/高效率账户，或明确写成“用户主观判断 vs 数据”的冲突测试；
- **judge 同源**：model-as-judge 与 Agent 同源，100% 不可信到“上线质量”级别；需要人工抽检与跨模型 judge；
- **评测 harness**：`--judge=evidence` 已是默认；下一步把 `qa:llm-rubric` 接进 CI，每次改 prompt/工具/上下文都跑一遍，记录通过率。
