# 数据模型：店铺、商品与推广计划

> 一句话：**账户是店铺，商品是独立实体，计划是商品的一种投放方式。**
> 一个店铺有多件商品；一件商品可以有多条推广计划；商品上下架与计划投放是两件事。

---

## 1. 对象关系

```text
店铺 / 千川账户（Account）
├─ 商品 A（在售，库存 498）── 推广计划 A1：标准推广 · 商品卡
│                          └─ 推广计划 A2：全域推广 · 直播间引流
├─ 商品 B（在售，库存 75）── 推广计划 B1：全域推广 · 短视频带货
├─ 商品 C（售罄，库存 0）── 暂无计划
└─ 商品 D（审核中 / 已下架）── 暂无计划
```

对应到本项目：

| 业务对象 | 代码 | 关键字段 | 示例 |
| --- | --- | --- | --- |
| 店铺 / 广告账户 | `Account` | `id`、`name`、`budget`、`balance`、`status`、`authorization`、`dataSources`、`lastSyncedAt`、`effectiveBalance`、`sharedWalletBalance` | 初见美妆旗舰店（已授权，千川报表 / 商品交易 / 素材） |
| 商品 | `Product` | `id`、`accountId`、`name`、`price`、`status`、`stock`、`category` | `prod_..._1` 轻透防晒霜 ¥159，在售，库存 498 |
| 推广计划 | `Campaign` | `id`、`accountId`、`productId`、`mode`、`target`、`brandPlacement`、`budget`、`bid`、`bidStrategy`、`roiGoal`、`schedule`、`audience`、`creativeIds`、`learningPhase`、`changes` | 标准-轻透防晒霜-短视频带货 |
| 创意 / 素材 | `Creative` | `id`、`campaignId`、`type`（短视频/图片/直播间）、`hook`、`auditStatus`、`rejectReason`、`durationSeconds`、`createdAt`、`daily` | `cr_..._1` 短视频 · 真实测评 · 通过 |
| 素材日数据 | `CreativeDaily` | `date`、`cost`、`show`、`click`、`orders`、`revenue`、`netRevenue`、`netOrders`、`refundAmount`、`refundRate`、`completion5s` | 单条素材的消耗 / ROI / CTR / CVR / 5 秒完播 / 退款 |

### 素材数据怎么生成

- 素材不是独立随机：**每条素材的日数据相加 = 计划日数据**，计划相加 = 账户日数据；
- 素材原型（真实测评 / 场景种草 / 低价钩子 / 参数罗列 / 直播切片 / 达人同款）决定 CTR、CVR、退款、衰减的差异，但**原型参数不暴露给 Agent**，Agent 只能看到结果；
- 退款金额由净成交推导：`refundAmount = revenue - netRevenue`，保证 `净成交 ROI` 可对账；
- 图片素材没有 5 秒完播率（`completion5s = null`）；未过审/未投放的素材当天数据为 0；
- 校验命令：`node scripts/mock-invariants.mjs`（要求 0 处不一致）。

### 商品身份与跨账户重名

- 商品 ID 是 **账户内唯一**：`Product.accountId` + `Product.id`。
- 不同账户下出现同名商品（例如“蓝牙音响”）**不是同一个商品对象**：
  - 星野数码官方店（华南事业群 · 竞价）的蓝牙音响；
  - 星野数码品牌店（品牌营销中心 · 品牌）的蓝牙音响；
  - 两者 `accountId`、`productId`、计划、预算、负责团队都不同。
- 智能助手按 `productId` 建立，因此也是两个独立助手。
- 当前 mock 的商品名来自类目池，可能在不同账户复用；同名只是展示重名，`productId` 不同。生产环境应补 `sku` / 商家 `spuId` 做唯一标识。
- 如果业务要求“一个物理 SPU 跨账户只有一个负责人”，需要额外的 `merchantId` / `spuId` 把多个账户商品归并；当前最小模型不做，避免跨团队预算混在一起。

### 事业群与品牌营销中心

- 华东事业群 / 华南事业群：区域经营单元，负责本区域商家的竞价投放账户。
- 品牌营销中心：品牌广告团队，负责品牌广告账户；与两个区域事业群平级。
- 同一个商家可以同时有“竞价账户”和“品牌账户”，因此同名商品可能出现在两个团队，但归属不同账户，不是数据冲突。
- A 公司是服务商；GETmore 是智能体名称，不是组织层级。

### 商品状态

```ts
type ProductStatus = "在售" | "售罄" | "审核中" | "已下架";
```

- 只有「在售」商品可以被新计划挂载；
- 「售罄」不清空计划，但补货前不建议加预算；
- 「审核中 / 已下架」商品不应继续投放。

商品状态和计划状态是两套状态：

| | 商品 | 计划 |
| --- | --- | --- |
| 状态 | 在售 / 售罄 / 审核中 / 已下架 | 投放中 / 已暂停 / 审核中 / 已结束 |
| 操作 | 上下架、改价、补库存 | 改预算、出价、启停 |

## 2. 计划不是商品

真实投放里，优化师通常按「商品 + 投放方式 + 策略」命名计划，例如：

```text
标准-轻透防晒霜-短视频带货
全域-玻尿酸保湿精华-直播间引流
```

所以看到「标准-轻透防晒霜-短视频带货」时：

- **不是**这个店铺只卖防晒霜；
- 而是**这条计划**在推广防晒霜这个商品；
- 同一商品可以有多条计划；同一店铺可以有多件商品、多条计划。

本 Demo 修复了早期的数据问题：之前商品池是全局轮询的，会出现“美妆店推广徒步鞋”的错配；现在按店铺类目分配商品池，并为每个店铺生成独立商品目录。

### 2.1 品牌广告范围

品牌渠道的两个范围是**互斥子集**，不是“总量 vs 再乘一个比例”：

| UI 范围 | 含义 | 数据 |
| --- | --- | --- |
| 整体（不含搜索） | 品牌信息流等非搜索品牌广告 | `brandPlacement = 品牌信息流` 的计划 |
| 搜索 | 品牌搜索广告 | `brandPlacement = 品牌搜索` 的计划 |

- 两张表的消耗 / 展示 / 点击相加 = 品牌渠道总量；
- 账户数会变化：只有部分品牌账户投了搜索，所以「搜索」范围的账户数更少；
- 品牌计划 Tab 是**计划维度**，不是投放方式；一行是一条品牌计划；
- 品牌广告只有曝光、点击、CPM、CTR，不展示支付 ROI（无支付归因）；
- 早期 mock 曾用「整体 × 18%」模拟搜索，这会造成口径不一致，已移除。

## 3. 当前 Demo 的实现

- `PRODUCTS`：按账户生成 3–5 个商品，包含价格、类目、库存、上下架状态。
- `Campaign.productId`：计划通过商品 ID 关联商品，不再内嵌一份商品快照。
- 计划只从该店铺「在售」商品中选择；同一商品可被多条计划复用。
- 账户表格显示「N 个商品」；账户抽屉展示店铺全部商品（含未投），并标出在售 / 售罄 / 审核中 / 已下架。
- 商品行展示：价格、库存、计划数、消耗、ROI；计划行展示商品标签。
- 账户抽屉顶部汇总「共 N 个 · 在售 X · 在投 Y」。
- **商品管理**：支持新建、编辑、删除、改价、改库存、切换上下架状态；数据写入浏览器 `localStorage`。
- 有推广计划的商品**禁止删除**；可先改为售罄/下架并处理计划。修改商品名不会自动重命名历史计划（计划名是投放标签）。

示例（初见美妆旗舰店）：

```text
共 5 个 · 在售 4 · 在投 2
轻透防晒霜       在售  库存 498  1 个计划  消耗 34,699  ROI 4.83
玻尿酸保湿精华   在售  库存 75   1 个计划  消耗 32,070  ROI 4.78
氨基酸洁面乳     在售  库存 433  0 个计划
高光妆前乳       在售  库存 376  0 个计划
净澈卸妆油       售罄  库存 0    0 个计划
```

## 4. 多维分析口径：投放方式与推广目标

### 4.1 切片

- `Campaign.mode`：全域推广 / 标准推广（品牌为品牌预定单）。
- `Campaign.target`：推商品 / 推直播间。**短视频是创意形式，不是推广目标。**
- 当前 KPI 会按「投放方式 + 推广目标」重新计算，账户表、组织汇总、Top 账户都使用同一份切片。

### 4.2 对账

计划的日序列会**归一化到账户日序列**：同一账户下，所有计划的消耗 / 支付 / 订单 / 展示 / 点击，逐日加总严格等于账户日序列。因此：

- 各投放方式、各推广目标的拆分合计 = 账户 KPI；
- 计划表的消耗合计与账户表一致；
- 上下文里的拆分数字不会出现“加不起来”的情况。

### 4.3 数据可用性

不是所有“看起来有用”的字段都能从千川拿到。当前 mock 按以下边界生成：

| 数据 | 来源 | 可用性 |
| --- | --- | --- |
| 消耗、展示、点击、支付金额、订单数、支付 ROI、订单成本 | 千川报表 | 账户/计划/日粒度可用；约 5 分钟刷新 |
| 净成交金额、净成交订单、1 小时退款率 | 千川报表（需商品/交易授权） | 部分账户可用；未授权时为 `null`，不显示为 0 |
| 账户总余额、有效余额、共享钱包余额 | 千川账户/资金接口 | 有效余额、共享钱包可能因权限缺失为 `null` |
| 计划状态、预算、出价、出价策略、ROI 目标、时段、人群、学习期、审核原因 | 千川计划接口 | 计划配置可用 |
| 素材标题、类型、审核状态、拒绝原因 | 千川创意接口 | 部分账户有素材授权，缺失时明确显示“未同步” |
| 调整记录：时间、字段、before/after、操作人、原因 | 千川调整记录 | 可作为归因时间锚点 |
| 商品成本、毛利率、物流、退货、税费 | 商家 ERP / 财务 | **千川不提供**；当前项目不生成，也不据此判断绝对盈亏 |
| 竞品、行业大盘、自然流量增量 | 外部/实验 | **不提供**；不要编造 |

### 4.4 净成交与盈亏边界

- **支付 ROI** = 支付金额 ÷ 消耗；
- **净成交 ROI** = 净成交金额 ÷ 消耗；
- **1 小时退款率**是报表字段，不等于最终退货率；
- 净成交/退款依赖商品交易授权，缺失时只能显示 `--`，不能当 0；
- 千川没有商品成本、毛利、履约费用，所以**不能仅凭 ROI 判断绝对盈亏**；
- 如需盈亏平衡 ROI，必须由商家配置成本口径，作为独立的“经营分析”能力，而不是广告报表字段。

### 4.5 上下文与动作

- Copilot 上下文包含：当前切片 KPI、投放方式拆分、推广目标拆分、净成交/退款（仅授权账户）、数据健康、组织概览、Top 账户。
- 上下文会明确写出缺失字段、延迟账户、部分授权；缺失字段不得推断为 0。
- 新增 `set_mode` / `set_target` 两个看板动作，Copilot 可以直接切换切片。
- 千川原始数据不包含成本/毛利，因此上下文不会给出“盈利/亏损”结论。

## 5. 真实千川还差什么

1. **SKU / 规格**：同一商品的颜色、尺码、规格与对应库存。
2. **商品审核**：商品资质、类目审核、下架原因。
3. **库存同步**：售罄 / 补货与计划投放的联动策略。
4. **商品维度报表**：按商品聚合消耗 / ROI / 订单，而不只是按计划。
5. **商品操作**：改价、上下架、补库存属于店铺/商品侧动作，不是广告计划动作。

当前实现优先保证「店铺 → 商品（含状态） → 推广计划」这条主线可解释、可下钻，再在这个基础上接 Agent 操作。
