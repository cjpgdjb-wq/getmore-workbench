# 技能设计闭环：为什么做、怎么设计、和业务什么关系

> 2026-11 更新：技能已从 JSON 注册表改成 `agent/skills/<id>/SKILL.md` + `skill.json` 目录包；planner 从摘要选 0–2 个，专家需要时 `load_skill` 读全文，没选到回退关键词路由。

> 面试官不会只问“你做了哪些 skill”，会问：
> **为什么是这几个？怎么设计出来的？和投放业务什么关系？怎么证明有用？**

---

## 1. 一句话回答

> 我不是先写 prompt，而是先找优化师高频、但容易拍脑袋的决策：
> **学习期该不该降预算、整体 ROI 低时预算往哪挪、库存快断要不要停、退款异常要不要收、素材拒审要不要停、周报怎么复盘。**
> 然后把它拆成“触发 → 输入 → 步骤 → 工具 → 输出 → 失败处理 → 评测”，
> 再接到专家、工具和 Decision 上。
>
> 前三个已做到 10 个 case + 完整工具链 pass@3；后三个 5 个 case，退款/素材已接完整工具链 pass@3，周报为只读 pass@3。  
> 新增三个的背景、数据依据和取舍见 [外部调研与技能选择](market-research.md)。

## 2. 闭环长什么样

```text
业务问题
→ 技能假设（什么情况下、按什么顺序判断）
→ 绑定专家（analytics 找证据 / ads 提交动作）
→ 工具（查数、模拟、提交 Decision）
→ 优化师确认
→ 3–7 天实验
→ 复盘（继续/回滚）
→ 评测（skill 级 + 完整工具链）
→ 回写默认策略
```

这条链路里，技能不是“一段 prompt”，而是**把业务判断固定成可执行、可评测的流程**。

---

## 3. 学习期诊断

### 为什么做

学习期计划 ROI 低于目标时，优化师常见两种错误：

- 直接暂停：打断学习，后面更难起量；
- 继续加预算：还没验证，越投越亏。

### 怎么设计

```text
数据健康
→ 学习期天数
→ ROI / 订单成本 vs 目标
→ 消耗占比 / 库存 / 余额
→ 样本不足只观察
→ 样本够才降 10%，不直接暂停
```

关键设计：

- 不是“看到 ROI 低就停”，而是先确认是不是学习期；
- 不是“给一个建议”，而是给 `observe / reduce` 和护栏；
- 数据缺失、样本不足、库存/余额不足 → 只观察；
- 动作由 ads 提交待确认 Decision，不直接执行。

### 和业务什么关系

| 业务指标 | 技能怎么影响 |
| --- | --- |
| 学习期 ROI | 避免过早暂停；样本够才降预算 |
| 支付 GMV | 不直接暂停，减少 GMV 断崖 |
| 订单成本 | 用 ROI/成本对比目标判断 |
| 回滚率 | 动作有护栏，3 天可回滚 |

### 怎么证明

- skill 级：10 个 case，**10/10**；
- 完整工具链：analytics + ads → 查数 → simulate → 预算 -10% 待确认 → 无暂停，**pass@3 3/3**。

### 面试 30 秒

> 学习期计划最容易误停。我做的不是“ROI 低就停”，而是先看数据健康、学习期天数、样本、库存和余额；样本不够只观察，够了才降 10%，不直接暂停。动作走 Decision，优化师确认后才执行。

## 4. 预算重排

### 为什么做

整体 ROI 低时，优化师常常：

- 只降预算，不告诉钱去哪；
- 凭感觉加给“看起来高 ROI”的账户；
- 没有 donor/recipient 依据，也没有总预算约束。

### 怎么设计

```text
数据健康
→ 账户 ROI / 目标 / 消耗
→ 找 1 个低 ROI 高消耗 donor
→ 找 1 个 ROI 高于目标、库存/余额有空间的 recipient
→ simulate 两侧
→ donor -10% + recipient +10% 两个 Decision
→ 不暂停、不增加总预算、最多 2 个动作
```

关键设计：

- 不是“只降”，而是“降一个、加一个”；
- 不加总预算，避免变成变相放量；
- 没有清晰 donor/recipient → 只观察；
- 两个动作都要人工确认。

### 和业务什么关系

| 业务指标 | 技能怎么影响 |
| --- | --- |
| 账户 ROI | 从低 ROI 账户挪到高 ROI 账户 |
| 支付 GMV | 不暂停、不增加总预算，控制风险 |
| 预算使用率 | 检查余额和库存，避免加到接不住 |
| 回滚率 | 两个 Decision 都可独立回滚 |

### 怎么证明

- skill 级：10 个 case，**10/10**；
- 完整工具链：donor 18,000→16,200；recipient 19,800→21,780；两个 Decision，**pass@3 3/3**。

### 面试 30 秒

> 预算重排不是“整体 ROI 低就一刀切降预算”。我先找低 ROI 高消耗的 donor，再找 ROI 高于目标、库存和余额有空间的 recipient；先模拟两侧，再提交一降一加两个待确认动作，不暂停、不增加总预算。

## 5. 库存止损（第三个）

### 为什么做

高消耗计划 + 低库存，是商家最痛的风险组合：继续投会退款、差评、履约压力；直接停又可能误伤。

### 怎么设计

```text
查计划消耗/状态
→ 查商品库存/可售天数
→ 库存 ≤3 天：暂停
→ 库存 4–7 天：降 20%
→ 库存充足/数据缺失：只观察
```

### 和业务什么关系

| 业务指标 | 技能怎么影响 |
| --- | --- |
| 库存可售天数 | 直接触发暂停/降预算 |
| 退款率 | 低库存继续投会推高退款 |
| 支付 GMV | 暂停会损失短期 GMV，但避免履约风险 |
| 计划消耗 | 先停高消耗计划，减少无效花费 |

### 怎么证明

- skill 级：10 个 case，**10/10**；
- 完整工具链：查计划/库存 → 暂停或降 20%，不加预算，**pass@3 3/3**。

### 为什么先做这三个

- 学习期、预算、库存，是优化师每天都会碰到的三个决策；
- 都能用现有工具完成“查数 → 模拟 → Decision”；
- 都能用 case + 完整工具链验证；
- 调研后又补了退款、素材拒审、周报：前两个接完整工具链，周报只读。  
  完整取舍见 [外部调研](market-research.md)。

**不是技能越多越好，而是每个都能说清：为什么、怎么设计、和业务什么关系、怎么证明。**

---

## 6. 设计原则

1. **技能不是 prompt**：有触发、输入、步骤、工具、输出、失败处理、评测；
2. **技能不直接执行**：只提交 Decision，优化师确认；
3. **技能有业务指标**：ROI、GMV、订单成本、回滚率；
4. **技能有失败边界**：数据缺失/样本不足/库存不足 → 只观察；
5. **技能可评测**：5–10 个 case + skill 级/工具链 pass@3；
6. **技能可编辑/导入**：能力中心独立管理；
7. **技能可路由**：[Skill Router](skill-router.md) 决定什么时候注入。
