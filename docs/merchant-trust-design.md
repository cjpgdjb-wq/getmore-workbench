# 让商家愿意把预算交给 Agent：可信投放控制台

> 产品设计文档 · 面向「巨量投放 Agent」的商家信任问题
> 配套文档：[岗位拆解与项目打法](agent-pm-fit.md)

---

## 0. 一句话

**信任不是“让商家相信模型更聪明”，而是“让商家相信一套可授权、可预演、可熔断、可对账、可退出的机制”。**

所以这个产品不叫“AI 投手”，叫**可信投放控制台**：Agent 负责分析和提案，商家负责定边界；每一笔钱都在授权内，每一个判断都有证据，每一次执行都可回滚，每一个预测都可对账。

---

## 1. 问题：商家到底不信任什么

### 1.1 公开信号：不是“AI 不行”，是“AI 不可信”

- **广告主不敢把程序化投放交给 LLM Agent**：Digiday 在 2025 年 12 月的报道里，多位 agency 高管明确说“不会把 programmatic activation 托付给基于 LLM 的 Agent”，首要原因是幻觉——一个小数点错误就可能是财务灾难，而且是“人被开掉，不是 AI”。他们愿意让 Agent 做的是 insight、analysis、ideation，不是直接花钱。[来源](https://digiday.com/media-buying/the-case-against-ai-agents-for-programmatic-ad-buying/)
- **投手面对的是“黑盒”**：一位做了四年投放的投手说，“全域推广就是个黑盒，我根本不知道能控制什么。” 千川·乘方发布后，AI Agent 接管了更多投放决策；有案例里，投手在爆发期关掉了跑量最好的 AIGC 素材，打断了系统的探索进程，当天 GMV 跌 20%，次日跌 55%。平台给的回复是标准话术“建议优化素材，保持投放稳定”，没人知道问题出在哪。[来源](http://www.niaogebiji.com/article-707865-1.html)
- **程序化广告的“黑箱”= 自动浪费**：预算投进去，曝光/点击“达标”，但品牌方追问“曝光来自哪里、多少是真人”，没人能给出确切答案。[来源](https://wap.cnki.net/touch/web/Journal/Article/SYCG202624001.html)
- **平台自己也知道信任是底座**：巨量引擎《2025 商业信任与安全治理报告》把“信任”作为穿越周期的基石，强调全链路治理、透明化、以 AI 治 AI；这说明“信任”不是某个产品的加分项，而是平台级议题。[来源](https://www.news.cn/tech/20260206/c210e727eb234c83bcaf265c2836d7a8/c.html)
- **乘方把“托管”推得更远**：千川·乘方用“千策/千意/千寻”做预算与 ROI 调度、AI 内容与诊断、增量推荐；商家只需设定整体预算与综合 ROI，系统自动分配。自动化越深，商家“看不懂、控不住”的焦虑越强。[来源](https://finance.sina.com.cn/jjxw/2025-12-15/doc-inhavwnp4307756.shtml)

### 1.2 六种不信任

| 类型 | 商家心里的问题 | 典型表现 |
| --- | --- | --- |
| **结果不可预期** | “它会不会拿我的钱做实验？” | ROI 波动、探索期、冷启动、预算跑飞 |
| **过程不可见** | “它为什么这么干？” | 黑盒、只有结论没有依据、口径对不上 |
| **权限不可控** | “我能叫停吗？能限制吗？” | 没有预算上限、没有止损、没有一键停 |
| **责任不可追** | “出了事谁负责？” | 不知道谁批的、不知道错在哪、没人赔 |
| **能力不可评** | “它凭什么让我信？” | 没有历史战绩、没有准确率、没有同行对比 |
| **关系不可逆** | “我能不能走？” | 数据锁死、权限收不回、换不掉 |

### 1.3 一个关键判断

> **商家不是不接受自动化，而是不接受“不可逆的自动化”。**

他们真正怕的不是“AI 算错一次”，而是：

1. 算错的结果不可控（花超了、跑飞了、停错了）；
2. 算错的过程不可见（不知道为什么，没法复现）；
3. 算错的权限收不回（叫不停、限不住、改不了）；
4. 算错的责任不可追（没人认、没人赔、没人改）；
5. 算对的能力不可证（这次是运气还是能力）；
6. 想退出的时候退不出（权限、数据、习惯都被锁死）。

所以，信任设计的对象不是“模型准确率”，而是**决策的可控性、过程的可见性、责任的可追溯性、能力的可验证性、关系的可退出性**。

## 2. 设计主张：从“相信模型”到“相信机制”

### 2.1 信任的四个来源

组织行为学里经典的信任模型是 **能力（ability）× 善意（benevolence）× 一致性（integrity）**。放到投放 Agent 上，还要加一个 **可预测性（predictability）**：

| 信任来源 | 商家要看到的证据 | 产品机制 |
| --- | --- | --- |
| **能力** | 它真的能提升 ROI / 省钱 | 影子模式、历史战绩、预测校准、同行基准 |
| **善意** | 它站在我这边，不是只想让我多花钱 | 商家定义目标函数、“不投放”建议、独立审计、不靠消耗拿激励 |
| **一致性** | 它说到做到，不会越界 | 授权书、护栏、审计、承诺可验证 |
| **可预测性** | 我知道它什么时候会做什么 | 信任阶梯、风险分级、熔断、冷静期 |

### 2.2 五个可验证承诺

产品对商家只承诺五件事，每件都能被验证：

1. **可懂**：每个结论都能下钻到数据、口径、时间和样本；不知道就说不知道。
2. **可控**：花多少钱、做什么动作、到什么程度，都由授权书定义；随时可停。
3. **可证**：每个预测都登记，T+1/T+3/T+7 对账；准确率公开，不是自说自话。
4. **可退**：任何动作可撤销，权限可收回，数据可导出，合作可结束。
5. **可长**：信任按额度给，不按功能给；做得好可以扩权，做不好自动降权。

### 2.3 信任栈：五层，每层回答一个问题

```text
┌─────────────────────────────────────────────┐
│ 5. 关系可信：激励对齐 / 责任 / 退出          │  “它是不是和我一伙的？”
├─────────────────────────────────────────────┤
│ 4. 结果可信：预测 vs 实际 / 校准 / 事故复盘   │  “它到底有没有用？”
├─────────────────────────────────────────────┤
│ 3. 执行可信：授权 / 护栏 / 审批 / 熔断 / 回滚 │  “它会不会乱来？”
├─────────────────────────────────────────────┤
│ 2. 推理可信：证据 / 反事实 / 不确定性 / 替代  │  “它为什么这么判断？”
├─────────────────────────────────────────────┤
│ 1. 数据可信：来源 / 口径 / 新鲜度 / 完整性     │  “数对不对？”
└─────────────────────────────────────────────┘
```

大多数“AI 投放”产品只做了第 2–3 层（解释 + 确认），但商家真正卡住的是第 4–5 层（结果对账 + 关系/激励）。**信任的短板在最后两层。**

### 2.4 设计原则

1. **先分析，后建议，再执行，最后对账**：分析是信任的入口，执行是信任的变现。
2. **默认不花钱**：任何花钱动作都需要授权；没有授权，Agent 只能看和说。
3. **不干预也是一等公民**：在探索期/学习期，“建议不动”可能比“建议加预算”更有价值。
4. **信任按额度给，不按功能给**：不是“开通自动投放”，而是“这 5 万块、这 3 个动作、这 14 天，交给你”。
5. **每个预测都要能被对账**：没有预测的动作，不算 Agent 的决策，只是执行。
6. **错误主动暴露**：不要等商家发现；主动报错、主动止损、主动复盘。
7. **平台激励必须对齐商家目标**：否则再好的解释也是“黄鼠狼给鸡拜年”。

### 2.5 分析是信任的入口：先让商家敢看

商家第一次用 Agent，通常不是让它花钱，而是让它回答“为什么 GMV 掉了”“哪个计划该停”“预算怎么分”。分析不花钱，是建立信任成本最低的场景。分析信任需要六个条件：

| 条件 | 商家的问题 | 产品机制 |
| --- | --- | --- |
| **口径对齐** | “为什么和你后台不一样？” | 同源数据、口径卡、差异解释 |
| **可下钻** | “这个结论怎么来的？” | 结论 → 指标 → 维度 → 明细，三层下钻 |
| **不确定性** | “你有多确定？” | 数据新鲜度、样本量、置信区间、缺失说明 |
| **反事实** | “如果不动会怎样？” | 不行动基线、对照、历史回放 |
| **可复现** | “下次还能复现吗？” | 保存为 skill/报告、版本化、重跑 |
| **可质疑** | “我能挑战你吗？” | 追问 why / what if / show data；Agent 必须承认不知道 |

> 先让商家在“不花钱”的分析里体验到“它说得清、找得到、可复现”，再谈执行授权。这就是信任阶梯 L0/L1 的价值：**分析不是执行的附属品，而是信任的入口。**

## 3. 产品架构：一个信任账户 + 四份合同 + 一个执行层 + 一个阶梯

### 3.1 总览

```text
                       ┌──────────────────────────────┐
                       │        信任账户 Trust Account  │
                       │  目标 · 预算 · 损失上限 · 动作范围 │
                       └──────────────┬───────────────┘
                                      │
        ┌───────────────┬─────────────┼─────────────┬───────────────┐
        ▼               ▼             ▼             ▼               ▼
   ┌─────────┐    ┌─────────┐   ┌─────────┐   ┌─────────┐    ┌─────────┐
   │ 授权合同 │    │ 证据合同 │   │ 执行层   │   │ 对账合同 │    │ 退出合同 │
   │ Mandate │    │ Evidence │   │ Execute │   │ Ledger  │    │  Exit   │
   └─────────┘    └─────────┘   └─────────┘   └─────────┘    └─────────┘
        │               │             │             │               │
        └───────────────┴──────┬──────┴─────────────┴───────────────┘
                                ▼
                       ┌──────────────────┐
                       │   信任阶梯 L0–L4  │
                       │ 观察→建议→审批→自动→托管 │
                       └──────────────────┘
```

> 执行层不是第五份合同：它是把授权、证据、对账、退出落到具体动作里的机制——审批矩阵、探索保护、熔断、回滚。

### 3.2 一句话解释四份合同

| 合同 | 回答的问题 | 核心对象 | 商家看到的界面 |
| --- | --- | --- | --- |
| **授权合同** | 你能花多少、做什么、到什么程度？ | `Mandate` | 授权书（滑杆 + 白话解释） |
| **证据合同** | 你凭什么这么判断？ | `Evidence` | 提案详情（依据/反事实/置信度） |
| **对账合同** | 你说的和实际差多少？错了怎么办？ | `Prediction` / `Actual` | 对账簿 + 信任周报 |
| **退出合同** | 我能不能停、撤、走？ | `Revoke` / `Export` | 一键暂停/撤销/导出 |

> 执行层是把这四份合同变成动作的机制，见 §4.3。

## 4. 四份合同 + 执行层：详细设计

### 4.1 授权合同（Mandate）：把“信任”变成可计算的额度

#### 4.1.1 设计要点

商家不是给 Agent 一个“开关”，而是给它一张**有额度、有范围、有期限、可撤销的授权书**。

```ts
interface Mandate {
  id: string;
  merchantId: string;
  accountIds: string[];
  objective: {
    primary: "综合ROI" | "净成交ROI" | "GMV" | "利润" | "新客数";
    target: number;
    floor: number;          // 不可破的底线
  };
  budget: {
    totalCap: number;       // 本期最多花多少
    dailyCap: number;       // 单日最多花多少
    maxLossCap: number;     // 本期最多亏多少（学习成本）
    maxSingleAction: number;// 单次动作最大金额
  };
  allowedActions: Array<"budget" | "bid" | "pause" | "resume">;
  forbidden: Array<"brand_budget" | "new_plan" | "creative_change" | "cross_account">;
  approval: {
    low: "auto" | "approve";
    medium: "approve" | "approve_with_check";
    high: "approve_with_check" | "dual";
  };
  window: { start: string; end: string; blackoutDates: string[] };
  autonomyLevel: 0 | 1 | 2 | 3 | 4;
  status: "draft" | "active" | "paused" | "revoked" | "expired";
  createdBy: string;
  approvedBy: string;
}
```

#### 4.1.2 四层额度

| 层级 | 作用 | 示例 |
| --- | --- | --- |
| **总预算上限** | 本期最多花多少 | 本月 50,000 元 |
| **单日上限** | 防止一天跑飞 | 每天 3,000 元 |
| **单次动作上限** | 防止一笔改太多 | 单次预算调整 ≤ 2,000 元 |
| **最大损失上限** | 允许的学习成本 | 本期最多亏 3,000 元（6%） |

> “最大损失上限”是信任设计里最容易被忽略、但最重要的一条：它把“我怕亏”变成“我知道最多亏多少”，把不可控的恐惧变成可承受的成本。

#### 4.1.3 授权书界面（白话版）

```text
┌──────────────────────────────────────────────────────────┐
│  授权书 · 轻氧家居旗舰店                    状态：生效中  │
├──────────────────────────────────────────────────────────┤
│  目标        综合 ROI ≥ 3.5（底线 3.0）                   │
│  本期预算    ¥50,000        单日上限 ¥3,000              │
│  最大损失    ¥3,000（6%）   单次动作 ≤ ¥2,000             │
│  允许动作    ☑ 改预算  ☑ 调出价  ☑ 暂停  ☐ 新建计划       │
│  排除        ☑ 品牌预算  ☑ 大促日  ☑ 跨账户               │
│  审批        低风险：自动   中风险：确认   高风险：确认+核对 │
│  有效期      2026-11-01 ~ 2026-11-30                      │
├──────────────────────────────────────────────────────────┤
│  当前自主权  L2 提案审批  →  再完成 2 周无事故可升 L3      │
│  [ 修改授权 ]  [ 暂停 ]  [ 撤销授权 ]  [ 导出授权书 ]      │
└──────────────────────────────────────────────────────────┘
```

#### 4.1.4 关键规则

- **硬上限不可越**：任何动作超出额度，直接拒绝，不是“提示”。
- **软上限可申请**：商家可以临时提额，但必须显式确认，且留痕。
- **额度按账户/商品拆**：避免“总额度够、单个账户跑飞”。
- **品牌/大促/新品默认排除**：这些场景的试错成本高，先人工。
- **授权有期限**：默认 30 天，到期自动失效，避免“一次授权，永久放权”。

### 4.2 证据合同（Evidence）：让每个判断都能被质疑

#### 4.2.1 三层证据

| 层 | 内容 | 商家的问题 | 产品呈现 |
| --- | --- | --- | --- |
| **数据层** | 来源、口径、时间、样本量、缺失 | “数对吗？” | 每个数字可点开，显示定义/来源/更新时间 |
| **逻辑层** | 为什么是这个动作、反事实、替代方案 | “为什么这么干？” | 结论 + 3 条依据 + “如果不做会怎样” |
| **责任层** | 谁批准、错了怎么办、怎么回滚 | “出了事谁负责？” | 审批人、回滚方案、损失上限、赔付规则 |

#### 4.2.2 提案详情的标准结构

```text
┌──────────────────────────────────────────────────────────┐
│  Agent 提案：账户日预算 +8%                   风险：中     │
├──────────────────────────────────────────────────────────┤
│  变更    ¥11,000 → ¥11,880 / 日（+880，+8%）              │
│  目标    综合 ROI ≥ 3.5；当前 3.6                          │
│  依据    ① 近 7 天 ROI 3.6，高于目标 0.1                  │
│          ② 库存可售 12 天，高于 7 天安全线                │
│          ③ 净成交已授权，退款率 4.2%（行业均值 6%）        │
│  反事实  不动：预计 ROI 3.4–3.7；加 8%：3.5–3.8           │
│  不确定  置信度 72%；主要风险：素材衰退、竞争加剧          │
│  数据缺口 商品成本未接入，无法判断绝对利润                 │
│  回滚    执行后 24h 内可一键回滚；回滚后预算恢复原值        │
│  责任    审批人：你；损失上限：¥3,000；超出自动熔断         │
├──────────────────────────────────────────────────────────┤
│  [ 确认执行 ]  [ 修改幅度 ]  [ 拒绝 ]  [ 先观察 24h ]      │
└──────────────────────────────────────────────────────────┘
```

#### 4.2.3 关键规则

- **没有工具返回的数据，不许写数字**：事实必须可追溯到工具结果。
- **缺失不是 0**：净成交未授权、成本未接入、数据延迟，必须显式写“不知道”。
- **给区间，不给假精确**：预测用区间 + 置信度，不用“预计提升 23.7%”这种伪精确。
- **给替代方案**：至少一个“不行动”的选项，避免 Agent 只会“加预算”。
- **解释给商家听，不是给算法听**：用“库存能卖几天”“这周多赚多少”，不用“CTR/CVR/ECPM”堆砌。

### 4.3 执行层（Controlled Execution）：让合同在动作里生效

#### 4.3.1 风险分级与审批矩阵

| 风险 | 例子 | 默认处理 | 商家看到的 |
| --- | --- | --- | --- |
| **低** | 下调预算 ≤5%、恢复计划 | 额度内自动 | 事后通知 + 可回滚 |
| **中** | 上调预算 ≤10%、调出价 ≤10% | 需确认 | diff + 依据 + 反事实 |
| **高** | 预算接近上限、单计划占消耗 >50%、库存 <7 天 | 确认 + 核对清单 | 额外风险提示 + 勾选 |
| **禁止** | 品牌预算、跨账户、新建计划、改素材 | 直接拒绝 | 说明原因 + 人工入口 |

#### 4.3.2 探索保护：解决“人把 AI 带崩”

鸟哥笔记的案例里，投手在爆发期关掉最好的 AIGC 素材，打断了系统探索，GMV 两天跌 55%。这不是 Agent 的错，是**人机协作**的错。信任产品必须同时保护商家“不被 Agent 乱来”和“不被自己的手痒带崩”。

设计：

- **探索期识别**：学习期、冷启动、爆发前 1–2 小时，标记为“探索窗口”。
- **不干预建议**：Agent 可以输出“建议观察 2 小时，不做动作”，并给出理由和复查时间。
- **干预冷静期**：商家要暂停/大幅降价时，弹出“当前处于探索期，过去 3 天类似操作导致 ROI 下降 X%；预计影响 Y；建议 2 小时后再看”。
- **干预前预演**：先模拟“如果按你的操作，预计 ROI/GMV 变化”，再决定。
- **干预记录**：谁在什么时候手动改了什么，进入同一条时间线，方便归因。

> 这是信任设计里最反直觉、也最有价值的一条：**Agent 不只是“帮你花钱”，还可以“帮你忍住不乱花”。**

#### 4.3.3 熔断与止损：把最大损失写进产品

```text
触发条件（任一）：
- 实际 ROI 连续 2 个统计窗口低于底线
- 当期损失达到 maxLossCap 的 80%
- 单日消耗超过 dailyCap 的 120%
- 同一账户 1 小时内被人工修改 ≥3 次
- Agent 动作失败率 > 20%

动作：
1. 立即暂停自动执行（不是暂停所有计划）
2. 冻结待确认提案
3. 推送“熔断说明”：发生了什么、可能原因、已采取什么、建议什么
4. 保留人工接管入口
5. 记录 TrustEvent，进入复盘
```

**关键**：熔断不是“全停”，而是“停止自动、保留人工”；不是“甩锅”，而是“先止损、再解释”。

#### 4.3.4 回滚与退出

- **单动作回滚**：任何已执行动作可一键回滚，保留 before/after。
- **批量回滚**：按 run / 时间窗 / 账户回滚。
- **授权撤销**：一键撤销授权，Agent 立即降为只读。
- **数据导出**：授权书、决策、证据、对账、事故报告，全部可导出。
- **删除权**：商家可要求删除非必要数据；保留审计所需的最小集。

### 4.4 对账合同（Ledger）：信任的复利

#### 4.4.1 预测登记

每个提案在执行前登记：

```ts
interface Prediction {
  id: string;
  decisionId: string;
  metric: "ROI" | "GMV" | "CPA" | "净成交ROI";
  baseline: number;       // 不做动作的预测
  predicted: number;      // 做动作的预测
  low: number; high: number; // 区间
  confidence: number;     // 0–1
  horizon: "T+1" | "T+3" | "T+7";
  method: "历史回放" | "同类账户" | "模型预测";
  dataGaps: string[];
}
```

#### 4.4.2 对账簿

```text
┌────────────────────────────────────────────────────────────────┐
│  对账簿 · 11 月第 2 周                                           │
├──────────┬────────┬────────┬────────┬────────┬─────────────────┤
│ 决策      │ 预测ROI │ 实际ROI │ 偏差    │ 判定    │ 备注            │
├──────────┼────────┼────────┼────────┼────────┼─────────────────┤
│ 预算+8%   │ 3.6    │ 3.5    │ -2.8%  │ 命中    │ 库存/退款正常    │
│ 暂停计划A │ 3.8    │ 3.4    │ -10.5% │ 偏差    │ 竞品降价，非动作 │
│ 出价-10%  │ 3.2    │ 3.3    │ +3.1%  │ 命中    │ 学习期恢复       │
│ 预算+20%  │ 3.1    │ 2.6    │ -16.1% │ 错误    │ 库存不足，已回滚 │
└──────────┴────────┴────────┴────────┴────────┴─────────────────┘
本周：12 个决策，9 命中，2 偏差，1 错误；预测平均误差 6.8%
累计：86 个决策，命中率 78%；90% 区间覆盖率 84%
```

#### 4.4.3 校准与能力证明

- **校准曲线**：预测值 vs 实际值；理想是对角线。
- **分场景**：冷启动/爆发/稳定、加预算/降预算/暂停/调价，各自准确率。
- **分行业/类目**：避免“平均准确率”掩盖短板。
- **公开战绩**：商家能看到“这个 Agent 在我这类账户上的历史表现”，不是平台自吹。
- **反向指标**：不仅看“预测准”，还要看“该不该做”——动作质量比预测精度更重要。

#### 4.4.4 事故与信任修复

信任不是靠“一直不出错”，而是靠“出错后怎么处理”。

```text
事故分级：
P0：资金/品牌/合规重大损失 → 1 小时内告知 + 人工接管 + 赔偿
P1：单账户损失超上限 → 4 小时内告知 + 回滚 + 复盘
P2：预测偏差 >20% → 24 小时内告知 + 解释 + 调整
P3：解释不清/数据缺口 → 周报汇总 + 改进

修复五步：
1. 承认：发生了什么，影响多大，不甩锅
2. 解释：根因是什么，是模型/工具/流程/人
3. 补偿：按规则赔付/减免/赠券
4. 改变：具体改了什么，什么时候生效
5. 验证：下一周期怎么证明改好了
```

### 4.5 退出合同（Exit）：信任的底线

- **一键暂停**：Agent 立即停止自动执行，保留只读分析。
- **一键撤销授权**：所有权限收回，待确认提案作废。
- **一键回滚**：按时间窗/账户/动作批量回滚。
- **一键导出**：授权书、决策、证据、对账、事故报告。
- **数据可删除**：非审计必需的数据可删除；审计数据保留期限明确。
- **不锁死**：不强制绑定支付、不强制续约、不隐藏退出入口。

> 商家愿不愿意用，很多时候不取决于“你有多好”，而取决于“我能不能随时走”。**退出权是信任的前提，不是信任的例外。**

## 5. 信任阶梯：从观察到托管

### 5.1 五级阶梯

| 级别 | 名称 | Agent 能做什么 | 商家做什么 | 适合谁 |
| --- | --- | --- | --- | --- |
| **L0** | 观察 | 只读分析、回答、复盘 | 看、问、判断 | 第一次接触 |
| **L1** | 建议 | 给建议 + 证据，不执行 | 自己执行 | 有投手/服务商 |
| **L2** | 提案审批 | 生成动作提案，人确认后执行 | 审批/修改/拒绝 | 大多数商家 |
| **L3** | 额度内自动 | 授权内自动执行，异常才找人 | 设额度、看周报 | 成熟商家 |
| **L4** | 托管 | 更大额度内自动，人工周度复盘 | 定目标、季度复盘 | 小商家/成熟品牌 |

### 5.2 升级与降级规则

| 升级 | 条件（示例） | 降级 | 条件（示例） |
| --- | --- | --- | --- |
| L0→L1 | 数据准确率 ≥95%，连续 2 周 | L1→L0 | 数据口径错误 ≥3 次/周 |
| L1→L2 | 建议采纳率 ≥60%，连续 4 周 | L2→L1 | 连续 2 周采纳率 <30% |
| L2→L3 | 20+ 审批动作，预测误差 ≤15%，0 P0/P1 事故 | L3→L2 | 单次损失 > 上限 50%，或误停 ≥2 次 |
| L3→L4 | 8 周稳定，校准 ≥85%，商家主动申请 | L4→L3 | 预测误差 >25% 连续 2 周，或商家投诉 |

> 信任是“挣来的”，不是“开通的”。升级要慢，降级要快；**降级不是惩罚，是保护**。

### 5.3 为什么用“阶梯”而不是“开关”

- 商家对 Agent 的信任不是二元的；有人愿意让它分析，有人愿意让它提案，有人愿意让它自动改预算。
- 阶梯把“信任”变成可运营的指标：多少商家在 L1、多少升到 L2、多少降级。
- 阶梯让产品有“成长感”：商家看到“再 2 周无事故可升 L3”，比“开通自动投放”更有说服力。
- 阶梯也是风险控制：不同级别对应不同额度、不同审批、不同监控。

## 6. 角色与责任：信任是三方关系

### 6.1 三类用户

| 角色 | 关心什么 | 需要什么 | 界面策略 |
| --- | --- | --- | --- |
| **商家老板/店长** | 赚不赚钱、会不会亏、能不能停 | 结果、额度、异常、退出 | 白话、移动端、日报 |
| **投手/优化师** | 怎么调、为什么、效率 | 数据、工具、批量、diff |  dense、快捷键、多账户 |
| **服务商** | 多账户、权限、报告、续约 | 组织树、角色、白标报告 | 多租户、RBAC、导出 |

### 6.2 责任矩阵（RACI）

| 事项 | 商家 | 投手/服务商 | 平台 | Agent |
| --- | --- | --- | --- | --- |
| 定目标/预算 | **A** | C | I | — |
| 授权额度 | **A** | R | I | — |
| 策略建议 | C | C | I | **R** |
| 执行动作 | I | **A/R**（L2） | I | R（L3/L4） |
| 熔断/止损 | I | A | **R** | R |
| 事故复盘 | I | C | **A/R** | C |
| 数据/审计 | A | C | **R** | — |

> 关键：**Agent 不能成为责任的真空**。L3/L4 的自动动作，平台要承担“机制责任”（护栏、审计、赔付），商家承担“授权责任”，Agent 承担“执行责任”。三方都要有名字。

### 6.3 平台激励的原罪

这是最难、也最必须回答的问题：**Agent 是平台做的，商家凭什么相信它不偏向平台收入？**

设计上必须做四件事：

1. **目标函数由商家定义**：综合 ROI、净成交 ROI、利润、新客数，而不是“消耗最大化”。
2. **“不投放”是合法输出**：Agent 可以建议“这周不加预算”“这个计划先别停”；考核不只看消耗，也看节省和增量。
3. **独立审计/可导出账本**：商家可以导出全部决策与对账，第三方可复核；平台不能既当运动员又当裁判。
4. **收费透明**：不靠“多花钱”拿隐性激励；把服务费/佣金写清楚。

> 如果这四条做不到，再漂亮的解释也只是“信任表演”。**信任设计的第一性原理是激励对齐，不是 UI。**

## 8. 指标与实验

### 8.1 北极星指标

> **可信自动化消耗占比** = 在 L3/L4 授权内由 Agent 自动执行的消耗 / 账户总消耗。

它同时衡量“商家愿意给多少信任”和“Agent 能承接多少信任”。但必须配一个质量护栏：**预测校准误差（MAPE）** 和 **事故损失率**。否则“自动化占比”可以通过“什么都自动”刷高。

> 分析场景用先导指标：**周活跃分析商家、分析结论采纳率、分析复访率、口径投诉率**。先证明“分析值得看”，再谈“执行值得托”。

### 8.2 信任漏斗

```text
触达 → 试用分析 → 影子模式 → 首次授权 → 首次自动执行 → 30 天留存 → 扩权 → 推荐
```

| 阶段 | 指标 | 目标（示例） |
| --- | --- | --- |
| 试用分析 | 7 天内使用分析 ≥3 次 | ≥40% |
| 影子模式 | 开启影子并持续 2 周 | ≥30% |
| 首次授权 | 设置 Mandate | ≥25% |
| 首次自动 | 第一笔 L3 自动执行 | ≥15% |
| 30 天留存 | 仍在使用 | ≥60% |
| 扩权 | 额度/自主权提升 | ≥20% |
| 推荐 | NPS ≥40 或主动推荐 | ≥15% |

### 8.3 信任行为指标

| 指标 | 定义 | 为什么重要 |
| --- | --- | --- |
| 授权额度覆盖率 | Mandate 额度 / 月消耗 | 信任的“真金白银” |
| 自动执行占比 | L3/L4 自动动作 / 总动作 | 信任的深度 |
| 人工复核率 | 人工查看证据的比例 | 信任是否“有根据” |
| **橡皮图章率** | 审批 <3 秒且未查看证据 | 假信任/确认疲劳 |
| 撤销率 | 已执行动作被撤销 / 总动作 | 动作质量 |
| 拒绝率 | 被拒绝提案 / 总提案 | 判断分歧 |
| 预测校准 | MAPE、90% 区间覆盖率 | 能力可信 |
| 异常主动发现率 | Agent 先于商家发现异常 | 价值感 |
| 事故率/损失率 | P0/P1 事故、损失/消耗 | 安全底线 |
| 扩权率/降权率 | 升级/降级商家占比 | 信任增长/流失 |
| NPS/信任度 | 问卷 + 行为 | 主观感受 |

### 8.4 业务指标

- 增量 GMV / 增量 ROI（vs holdout / 合成控制）
- 低效消耗减少（ROI 低于底线的消耗占比）
- 节省时长（人工操作分钟数）
- 退款率/净成交 ROI（如果有授权）
- 库存周转/售罄率（避免只看广告指标）

### 8.5 护栏指标

- **超支率**：实际消耗 > 授权上限的比例（目标 0）
- **误停率**：被暂停但本可恢复的计划占比
- **过度依赖率**：Agent 错时人未发现的比例
- **确认积压**：待确认提案 >24h 的数量
- **解释投诉率**：商家对解释不满的工单占比

### 8.6 四个可验证假设

| 假设 | 实验单元 | 主指标 | 护栏 |
| --- | --- | --- | --- |
| H1：影子模式 + 对账能提升首次授权率（vs 直接确认弹窗） | 商家 | 14 天首次授权率 | 首次价值时间、工单 |
| H2：授权 + 熔断能提升自动执行占比，而不增加损失率 | 账户（分层） | 4 周自动执行占比 | 损失率、事故率 |
| H3：“不干预建议”能降低过度干预与 ROI 波动 | 账户-周（switchback） | 不必要的干预率、ROI 波动 | GMV |
| H4：校准展示能提升“适当依赖”（能发现 Agent 的错） | 商家（实验室 + 种子 badcase） | 错误发现率 | 过度依赖率 |

**实验难点**：不能为了 A/B 让商家少赚钱。所以优先用：
- **影子/回放**（不真实花钱）；
- **分层随机**（按类目/消耗层）；
- **stepped-wedge**（按组织逐步上线）；
- **switchback**（高频场景，时间片轮换）；
- **合成控制/双重差分**（无法随机时）。

### 8.7 离线评测

- **50 个历史 case**：冷启动/爆发/稳定/下滑；加预算/降预算/暂停/调价；数据缺口/品牌/库存。
- **6 维 rubric**：事实性、数据缺口、动作质量、校准、解释、安全。
- **双人标注**：资深投手 + 产品；计算 inter-rater reliability（Cohen's kappa）。
- **LLM-as-judge**：只用于事实性/解释初筛，必须用人工样本校准。
- **回归**：每次改 prompt/工具/上下文跑一遍，记录通过率与退化。
- **badcase 分类**：事实错、工具错、目标错、幅度错、时机错、解释错、安全违规、延迟。

### 9.5 演示脚本（5 步）

1. 商家设置授权书：月预算 5 万、最大损失 3 千、只允许预算/出价、品牌排除。
2. 开启影子模式：Agent 提案“暂停计划 A”，但不执行；对比人工选择。
3. 两周后看影子报告：Agent 与人工一致率、预测准确率、避免的损失。
4. 升级 L3：Agent 在额度内自动下调计划 B 出价 8%；商家收到通知，可回滚。
5. 触发熔断：ROI 连续低于底线，自动暂停自动执行；展示事故说明与回滚。

### 9.6 成功标准

- 商家能在 3 分钟内设置完授权书；
- 每个提案都能看到“预测/依据/反事实/回滚”；
- 每个已执行动作都有预测记录，T+3 能出对账；
- 熔断能在一个模拟场景中正确触发；
- 商家能一键撤销授权并回滚；
- 评测集覆盖 20+ case，baseline 可复现。

## 11. 风险与反脆弱

| 风险 | 表现 | 对策 |
| --- | --- | --- |
| **过度信任/自动化偏见** | 商家不看证据就点确认；Agent 错时人没发现 | 种子 badcase 测试、校准展示、强制“找茬”任务、随机复核 |
| **确认疲劳** | 每天几十个提案，变成橡皮图章 | 风险分级、批量摘要、日报、只对异常打扰 |
| **责任真空** | 出错后平台/商家/服务商互相甩锅 | RACI、赔付规则、审计留痕、合同 |
| **平台激励冲突** | 商家怀疑 Agent 只想让其多花钱 | 商家定义目标、“不投放”建议、独立审计、收费透明 |
| **数据隐私** | 跨账户/跨商家数据泄露 | 租户隔离、最小权限、脱敏、审计 |
| **模型漂移** | 大促/竞争变化导致预测失准 | 监控、再校准、降级、人工接管 |
| **信任表演** | 只做 UI 透明，不做机制 | 第三方审计、公开校准、可导出账本 |
| **小商家不会用** | 授权书太复杂，看不懂 | 默认模板、白话、移动端、服务商代设 |
| **品牌安全** | Agent 改素材/出价影响品牌 | 品牌预算/素材默认排除，人工复核 |

## 12. 面试怎么讲

### 12.1 1 分钟版本

> 商家不信任 AI 投放，不是因为它不够聪明，而是因为它的决策不可逆、过程不可见、权限不可控、责任不可追、能力不可证、退出不可行。
>
> 所以我设计的不是一个“更会分析的 Agent”，而是一套“可信投放控制台”：用**授权合同**限定它能花多少、做什么；用**证据合同**让每个判断可下钻、有反事实；用**对账合同**把预测和实际对上，错了能复盘；用**退出合同**保证商家随时能停、能撤、能走。然后用**信任阶梯**从观察到托管逐级放权。
>
> 一句话：**把信任从“相信模型”变成“相信机制”。**

### 12.2 三个必答题

**Q1：这和“加个确认弹窗”有什么区别？**
> 确认弹窗只解决“执行前看一眼”，解决不了“为什么信、错了怎么办、下次还信不信”。我做的是四份合同：授权（额度/范围）、证据（依据/反事实/不确定性）、对账（预测 vs 实际）、退出（撤销/导出）。确认只是执行层里的一个动作。

**Q2：商家凭什么相信平台做的 Agent？**
> 这是最难的问题，也是必须回答的。四件事：目标函数由商家定义（不是消耗最大化）、“不投放”是合法建议、账本可导出/可第三方审计、收费透明。如果激励不对齐，再好的解释都是信任表演。

**Q3：你怎么衡量“信任”？**
> 不看问卷，看行为：授权额度覆盖率、自动执行占比、扩权率、撤销率、橡皮图章率、预测校准、事故损失率。北极星是“可信自动化消耗占比”，但必须配校准和损失率做护栏，否则可以通过“什么都自动”刷高。

### 12.3 不要说的话

- “加个确认按钮就好了” —— 确认不等于信任。
- “模型更准就行了” —— 准确率是必要条件，不是充分条件。
- “信任是玄学” —— 信任可以被拆成可验证的机制和指标。
- “我们平台肯定不会坑商家” —— 商家不信誓言，信约束。
