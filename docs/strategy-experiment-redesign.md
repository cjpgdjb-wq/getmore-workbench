# 策略实验：优化师视角的重设计

> 结论先行：现在的「策略假设库」是**产品经理的研究简报**，不是优化师今天的动作清单。
> 优化师不会专门打开一个库看 p 值；他要的是：**在我正看的这个账户/计划上，接下来该试什么、试多大、什么时候看结果、错了怎么退。**

> **Phase 1 已落地**（2026-11-04）：策略实验抽屉、数据页账户/计划入口、3 个模板、开始/审批/进行中/复盘/回滚已跑通；H2/H3 收进「研究回放（产品视角）」。下一步：真实历史回放、检查点提醒、应用到同类。

> **UI 变更（2026-11-05）**：策略实验主入口已替换为 **GetMore 商品对话**：数据计划抽屉点 GetMore 后只预填 prompt，不自动开跑；发送后对话归属该商品助手。本文保留确定性实验引擎的设计与评测说明。

---

## 1. 现在为什么“用不上”

| 问题 | 表现 | 后果 |
| --- | --- | --- |
| **入口错** | 藏在「伙伴团队」左侧，叫「策略假设库」 | 优化师日常在数据页/计划列表，不会专门去开一个库 |
| **对象错** | 卡片是“18 个学习期计划、DiD +0.27、p<0.001” | 像研究论文，不像“我该不该动这个计划” |
| **没有绑定范围** | 没有 accountId / planId，没有“在我的账户上试” | 看完就完了，无法执行 |
| **没有生命周期** | 没有“待开始 / 进行中 / 待复盘 / 已结论” | 没有提醒、没有复盘、没有下一步 |
| **混了三种事** | H1 投放策略、H2 Agent 数据门禁、H3 审批交互放在一起 | 优化师只关心 H1；H2/H3 是产品/Agent 质量 |
| **只有回放，没有执行** | 回放是模拟实验，不产生 Decision/Operation | 和真实的投放、审批、审计脱节 |
| **没有“不做”的选项** | 每张卡都鼓励“验证” | 小账户样本不足，硬做实验反而浪费预算 |

一句话：**它回答的是“这个策略有没有统计显著”，不是“我今天该动哪个计划”。**

---

## 2. 优化师真正的工作流

```text
早上看数 → 找异常账户/计划 → 判断原因 → 决定动作 → 执行/审批 → 下午盯 → 晚上复盘
```

他真正会问的四个问题：

1. **哪个账户/计划值得动？**（不是“有哪些假设”）
2. **该动多少、动哪个方向？**（不是“p 值多少”）
3. **动完多久看、看什么、什么算好/坏？**（不是“置信区间”）
4. **错了怎么退、怎么证明是我的动作导致的？**（不是“实验组 vs 对照组”）

所以产品对象不应该是“假设”，而应该是**一个有范围、有动作、有止损、有复盘的小实验**。

---

## 3. 新定位：从「策略假设库」到「策略实验」

> **策略实验 = 在某个账户/计划上，用 3–7 天、有上限、可回滚的一次小验证。**

它解决三件事：

- **发现**：这个账户/计划，现在最值得试什么？
- **执行**：一键生成提案（走现有 HITL），或只加入观察；
- **复盘**：3/7 天后，告诉你继续、扩大、回滚，还是样本不足。

和现在的区别：

| 现在 | 重新设计后 |
| --- | --- |
| 研究简报 | 动作清单 |
| 独立假设库 | 从账户/计划上下文进入 |
| 3 张静态卡 | 按当前范围生成 2–3 个推荐 |
| 回放结果 | 真实执行 + 复盘 |
| p 值/CI 为主 | “继续/回滚/再观察”为主，方法折叠 |
| H1/H2/H3 混在一起 | 投放策略实验 vs Agent 质量实验，分开 |

---

## 4. 设计原则

1. **上下文优先**：从你正在看的账户/计划进入，不要求先找入口。
2. **动作优先**：每个实验必须有具体动作、成本上限、止损线、观察窗口。
3. **小且可逆**：默认 3–7 天、预算 ±5–10%、随时可停、可回滚。
4. **说人话**：默认只显示“建议 / 依据 / 成本 / 判断标准”；统计方法折叠到“方法”。
5. **闭环**：推荐 → 进行中 → 待复盘 → 已结论 → 应用/回滚；有提醒。
6. **不装精确**：样本不足就说“只观察”，没有对照就说“前后对比，不是严格 A/B”。
7. **两条 lane**：投放策略实验给优化师；Agent 质量实验给产品/评测，不占默认视图。

## 5. 信息架构与入口

### 5.1 入口优先级

| 优先级 | 入口 | 触发场景 | 形态 |
| --- | --- | --- | --- |
| **P0** | 数据页 · 账户/计划抽屉 | 正在看某个账户/计划，想知道“该不该动” | 右侧抽屉「策略实验」，自动带入 accountId/planId |
| **P0** | Agent 提案/回答 | Agent 说“建议暂停/加预算”，优化师想“先验证一下” | 提案下方「先小实验再执行」链接 |
| **P1** | 伙伴团队左侧 | 主动想看“本周有什么值得试” | 入口改名「策略实验」，展示推荐 + 进行中 + 已结论 |
| **P1** | 工作台右侧栏 | 日常扫一眼 | 「本周实验」卡片：2 个进行中 / 1 个待复盘 |
| **P2** | 通知/待办 | 实验到期 | 并入现有「待确认动作」/待办，不新建收件箱 |

**不做**：新的顶级 Tab「实验」。会让工作台更碎；优化师不需要多一个页面。

### 5.2 为什么用抽屉，不用大弹窗

- 实验是**上下文相关**的：优化师要一边看计划数据，一边决定试什么；
- 大弹窗会遮住数据表/计划详情；
- 右侧抽屉 460–520px，保留左侧数据可见；关闭后回到原位置。

## 7. 对象与生命周期

```ts
interface Experiment {
  id: string;
  templateId: string;
  title: string;
  question: string;
  scope: {
    accountId: string;
    planIds: string[];
    productId?: string;
  };
  baseline: { metric: string; value: number; window: string };
  proposal: {
    action: "budget" | "bid" | "pause" | "resume" | "observe";
    params: Record<string, number | string>;
    expected: string;
    costCap: number;
    durationDays: number;
  };
  design: {
    primaryMetric: string;
    guardrail: string;
    checkpoints: string[];   // D1 / D3 / D7
    method: "pre_post" | "matched_control" | "holdout";
    minSample: number;
    stopRule: string;
  };
  status: "suggested" | "running" | "readout" | "concluded" | "applied" | "reverted" | "dismissed";
  actionRef?: { decisionId?: string; operationId?: string };
  checkpoints: { day: number; at: number; metric: number; note: string }[];
  readout?: {
    effect: number;
    verdict: "positive" | "neutral" | "negative" | "insufficient";
    plain: string;
    confidence: "high" | "medium" | "low";
    recommendation: "continue" | "expand" | "revert" | "observe";
    stats: Record<string, number | null>;
  };
  owner: string;
  createdAt: number;
  startedAt?: number;
  endedAt?: number;
}
```

### 7.1 状态流转

```text
suggested
  ├─ 开始实验 → running（生成 Decision，走 HITL）
  ├─ 只观察   → running（observe，不生成 Decision）
  └─ 不感兴趣 → dismissed（记录原因）
running
  ├─ 到检查点 → readout
  ├─ 提前结束 → readout / reverted
  └─ 护栏破   → 自动停止 + 告警
readout
  ├─ 继续/扩大 → applied（写入策略/记忆）
  ├─ 回滚     → reverted（撤销操作）
  └─ 再观察   → running（延长）
```

### 7.2 关键规则

- **开始实验 = 生成一个 Decision**：沿用现有护栏、审批、审计、撤销；不新增写入口。
- **只观察 = 不生成 Decision**：只记录基线和检查点，适合预算小/样本不足。
- **止损线**：实验期消耗上限、ROI 底线、库存/余额；触发自动停止。
- **回滚**：复用 `undoOperation`；一键回到实验前。
- **样本不足**：直接给“只观察”或“扩大范围”，不硬做实验。
- **归因**：优先用同账户同期对照；没有对照就明确写“前后对比，非严格 A/B”。

## 8. 推荐引擎

### 8.1 输入

当前范围（accountId / planIds / productId）、近 7 天数据、学习期、预算使用率、ROI 趋势、消耗占比、库存、余额、数据健康、历史实验。

### 8.2 规则

| 模板 | 条件（示例） | 推荐动作 |
| --- | --- | --- |
| 学习期 | `learningPhase=学习中` + ROI < 目标 + 7d 消耗 ≥5,000 | 降预算 10% |
| 预算撞线 | 预算使用率 ≥90% + ROI ≥目标 + 库存 ≥7 天 | 加预算 10% |
| 高 ROI 低消耗 | ROI ≥目标+0.5 + 消耗占比 <20% | 加预算 5% |
| 低 ROI 高消耗 | ROI <目标-0.3 + 计划占账户消耗 >40% | 降预算 10% |
| 数据延迟 | 延迟 >15 分钟 + ROI 单日跌幅 >20% | 只观察（数据健康） |

### 8.3 排序

```text
优先级 = 影响金额（消耗 × ROI 缺口）× 置信度（数据完整/样本）
       ÷ 实验成本（预算风险 × 天数） × 可逆性
```

只展示 Top 2–3；其余收进「更多建议」。每个推荐必须写清“为什么是现在”。

### 8.4 不推荐的情况

- 样本不足（转化 <20/天、消耗 <3,000/7d）→ 只观察；
- 数据延迟/部分授权 → 先补数据；
- 品牌预算/大促/新品 → 人工，不做自动实验；
- 已有进行中的同类实验 → 不重复推荐。

## 9. 现有 3 个假设怎么处理

| 现在 | 新去处 | 原因 |
| --- | --- | --- |
| **H1 学习期分层干预** | 保留为「策略实验」的第一个模板 | 优化师真正会做的决策 |
| **H2 数据延迟门禁** | 移到「数据健康建议」/「研究回放（产品视角）」 | 这是 Agent 的判断门禁，不是投放策略 |
| **H3 高风险证据默认展开** | 移到「研究回放（产品视角）」/「评测」 | 这是审批体验/信任设计，不是优化师的投放实验 |

> 这三张卡本身没有错，错在**放在同一个入口、用同一种语言**。优化师只该看到 H1 这一类；H2/H3 给产品和评测。

新增两个优化师模板：

- 预算撞线：加预算 10% vs 保持；
- 高 ROI 低消耗：加预算 5% vs 保持。

## 10. 与现有系统集成

| 现有能力 | 复用方式 |
| --- | --- |
| `Decision` / `Denial` 护栏 | 开始实验生成 Decision；审批后才执行 |
| `Operation` / 撤销 | 回滚实验动作；审计里带 `experimentId` |
| `DataHealth` | 数据延迟/部分授权时只给“只观察”或“先补数据” |
| `Run` / 工作痕迹 | 实验执行、工具调用、审批都进痕迹 |
| 记忆 | 实验结论写回记忆（“轻氧家居：学习期降预算有效”） |
| 评测 | 实验结论变成评测用例；失败实验变反例 |
| 假设引擎 | 保留 `hypotheses.mjs`/`trials.mjs` 作为离线估计/回放；不作为默认 UI |

### 10.1 数据缺口门禁（已落地）

数据缺口不再只是“降置信”，而是分三级：

| 缺口 | 级别 | 是否阻断改投放 |
| --- | --- | --- |
| 商品交易未授权，无法算净成交/退款 | blocking | **是**：只能只观察 / 先补授权 |
| 账户仅部分授权，但所需数据可用 | warning | 否，提示 |
| 报表延迟 >15 分钟 | warning | 不阻断 7 天实验；实时判断需谨慎 |

门禁规则：

- 部分授权 + 商品交易缺失 → 合并成一条“商品交易未授权”，不再重复显示“账户仅部分授权”；
- 低 ROI / 高 ROI 放量类推荐需要 `商品交易`；缺失时 `canStart=false`；
- 开始实验时后端再次校验，不能只靠前端按钮；
- 只观察不受门禁影响。

## 12. 指标

**优化师行为**

- 推荐曝光 → 打开率；
- 打开 → 开始实验率；
- 实验完成率、按时复盘率；
- 继续/扩大/回滚比例；
- 不感兴趣原因分布。

**业务**

- 实验期增量 ROI/GMV；
- 避免的无效消耗；
- 节省的决策时间；
- 实验后 30 天留存。

**护栏**

- 实验超支率；
- 实验期损失超上限比例；
- 样本不足仍开实验的比例；
- 回滚失败率；
- 推荐被忽略率（判断推荐质量）。

> 我一开始做的是“策略假设库”，但发现优化师不会用：它藏在伙伴团队里，是一份研究简报，没有绑定账户，也没有复盘。
>
> 所以我把它重做成“策略实验”：从优化师正在看的账户/计划进入，系统给 2–3 个带动作、成本、止损、判断标准的小实验；开始实验会生成待确认提案，走现有 HITL；3–7 天后自动复盘，告诉他继续、扩大、回滚还是样本不足。产品经理看的是“假设是否成立”，优化师看的是“今天该不该动这个计划”。
